<FastAPI vs Uvicorn 역할 비교>

FastAPI: 실제 네트워크 통신을 처리하는 기능은 없으며, 들어온 요청에 대한 비즈니스 로직과 데이터 검증 등 웹 프레임워크의 역할에 집중합니다.

Uvicorn: 외부(클라이언트)에서 들어오는 HTTP 요청을 FastAPI로 전달하고, FastAPI의 응답을 다시 클라이언트에게 돌려주는 웹 서버 역할을 수행합니다.


<코드 설명 및 이해하기>

import os
from fastapi import FastAPI 등등

load_dotenv() 
.env 파일에 있는 환경변수(API 등)를 불러온다.
관례상 맨 위(import 직후)에 두는 이유는 환경변수 로드가 늦어져서 코드가 깨지는 문제를 방지하기 위해서이다.
getenv 호출 전에 작성해도 되지만 실질적으로는 맨 위에 두는게 안전하다.

app = FastAPI(docs_url=None, redoc_url=None) 
Swagger(/docs)와 ReDoc(/redoc) 자동 문서 페이지를 비활성화해서 API 구조가 외부에 노출되지 않도록 한다.
만약 문서가 보이게 하고 싶다면, (docs_url="/docs", redoc_url="/redoc") 라고 적용하면 된다.

--------> 임포트 및 초기 설정


origins = os.getenv("ALLOWED_ORIGINS").split(",")
.env의 ALLOWED_ORIGINS를 불러와서 허용할 프론트엔드 도메인들만 지정한다.

app.add_middleware(
    CORSMiddleware,
    allow_origins=origins,
    allow_methods=["*"],
    allow_headers=["*"],
)
메서드/헤더는 전체허용(*)이지만 origin은 제한되어 있어, 지정된 도메인에서만 해당 API를 호출할 수 있다.
allow_methods=["*"] : GET,POST,PUT,DELETE 등 모든 메서드의 크로스오리진 요청을 허용. 
/chat(POST), /messages/{id}(DELETE)처럼 여러 메서드를 사용하니까 메서드마다 일일이 나열하는 대신 편의상 *로 열어둠.
allow_headers=["*"] : 클라이언트가 요청에 담아 보내는 커스텀 헤더(Authorization, Content-Type 등)를 전부 허용. 

전체허용(*) 사용해도 괜찮은 이유는, allow_origins로 제한되어 있어 허용된 origin이 아니면 애초에 브라우저가 요청을 막기 때문이다.

주의할 점은 allow_credentials=True를 추가한다면, allow_origins에 * 못쓰고 allow_headers에도 *가 제한될 수 있다.
credentials는 브라우저가 요청에 자동으로 실어 보내는 '신원 정보'이다.
(쿠키(Cookie 헤더), HTTP 기본 인증 정보, 클라이언트 TLS 인증서)
Authorization: Bearer <token> 헤더를 프론트엔드 코드가 직접 만들어서 넣는 건 credentials에 들어가지 않는다. 하지만 로그인 방식을 쿠키 기반 세션으로 바꾼다면 브라우저 코드가 아래처럼 바뀐다.

fetch("https://api.example.com/chat", {
  method: "POST",
  credentials: "include",  // 쿠키를 자동으로 실어서 보내겠다는 옵션
  ...
})

이때 서버는 CORS 응답에 Access-Control-Allow-Credentials: true 를 함께 보내야 브라우저가 응답을 허용한다. 그리고 그 순간부터 브라우저 스펙이 아래처럼 된다.
Access-Control-Allow-Origin: * → 금지. 반드시 요청 origin을 그대로 명시해야 함 (예: https://myapp.com)
Access-Control-Allow-Headers: *도 일부 브라우저에서 와일드카드가 무시되고 명시적 헤더 나열을 요구

이런 규칙이 있는 이유는, 쿠키가 자동으로 넘어가는건 '로그인된 상태 그대로' 요청이 간다는 뜻이라 아무 origin(*)이나 허용해버리면 악성 사이트 혹은 사용자 브라우저를 통해 로그인된 세션으로 몰래 요청을 보낼 수 있기 때문이다. 그래서 브라우저가 credentials를 사용할거면 origin을 정확히 밝혀라라고 하는 것이다.

-------> 외부 클라이언트 initialization


security = HTTPBearer()

def get_current_user(credentials: HTTPAuthorizationCredentials = Depends(security)):
    try:
        result = supabase.auth.get_user(credentials.credentials)
        if not result.user:
            raise HTTPException(status_code=401, detail="Unauthorized")
        return result.user
    except Exception as e:
        print("AUTH ERROR:", e)
        raise HTTPException(status_code=401, detail="Unauthorized")

HTTPBearer() : 요청 헤더의 Authorization: Bearer <token>을 자동으로 파싱.
get_current_user : 토큰을 Supabase에 보내 실제 유효한 사용자인지 검증. 유효하지 않으면 401 에러.
또한, Depends(get_current_user) 형태로 다른 엔드포인트에 주입되어 로그인한 사용자만 접근 가능하도록 의존성(dependency) 역할을 한다.

-------> 인증(토큰 검증) 로직


class ChatRequest(BaseModel):
    message: str = Field(max_length=1000)
    room_id: str

/chat 엔드포인트에 들어올 요청 바디의 형태를 정의. Pydantic이 자동으로 타입 검증(문자열인지 뭔지)을 해주고 메시지 길이는 1000자로 제한해준다.


스키마(schema)란 데이터가 어떤 모양이어야 하는지를 나타내는 것. 
ChatRequest는 실제 값이 아니라 /chat으로 들어오는 요청 body는 이런 구조여야 한다는 틀을 정의한 것.
message: str = Field(max_length=1000) -> 문자열. 1000자 이하.
room_id: str -> 문자열.
